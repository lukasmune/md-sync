# md-sync

[![License: AGPL v3](https://img.shields.io/badge/License-AGPL_v3-blue.svg)](https://www.gnu.org/licenses/agpl-3.0)

## Overview

`md-sync` is a Python-based synchronization tool for Messe Düsseldorf exhibitor data. It retrieves directory listings for GIFA, METEC, THERMPROCESS, and NEWCAST, resolves company identities across multiple exhibition editions, and stores the normalized result in a centralized local SQLite database. It also provides edition-specific Excel exports and a test suite.

The repository is not a generic production integration layer yet. The configuration and current execution path are strongly centered on GIFA 2023, although several functions are written generically enough to accept a different event label or edition.

## What the Project Currently Does

The application currently:

- Fetches directory records from the Messe Düsseldorf JSON API using a letter-based traversal (`a` through `z`).
- Filters those records to only `type == "profile"` entries with matching event icons for a target event label such as `"GIFA 2023"`.
- Normalizes company names, countries, and cities for duplicate and identity matching.
- Creates rows in a `companies` table and reuses the same internal company ID across repeated records or later exhibitions.
- Writes exhibition participation records into an `exhibition_companies` link table keyed by company and exhibition.
- Stores event metadata in an `exhibitions` table (`event_name`, `edition`, `event_code`).
- Provides an Excel export of exhibition/company data.
- Includes tests that hit the live API and validate the database synchronization logic.

The directory payload currently exposes company name, country, city, location,
tags, premium status, event icons, exhibitor ID, and SEO ID. A live sample did not
contain email, telephone, website, or product classification fields.
The directory response does not contain these fields. The configured scraper
enriches each selected exhibitor through the VIS profile endpoint described below.

## Architecture

The project is a small, single-process data pipeline:

- Configuration constants live in [config.py](./config.py).
- Database schema and upsert logic live in [database.py](./database.py).
- The API client and event filtering logic live in [scraper.py](./scraper.py).
- Name/country/city normalization lives in [normalizer.py](./normalizer.py).
- The Excel export logic lives in [excel_export.py](./excel_export.py).
- The merge helper protecting internal sales fields lives in [sync.py](./sync.py).
- A helper script for duplicate inspection lives in [inspect_duplicates.py](./inspect_duplicates.py).

The main runtime flow is:

1. `scraper.fetch_directory_letter(letter)` requests a JSON directory page.
2. `scraper.fetch_exhibitors_by_event(event_label)` loops over all letters and filters records to those associated with the requested event.
3. `scraper.sync_event(...)` creates or reuses the exhibition row and then calls `database.sync_exhibitor(...)` for each record.
4. `database.sync_exhibitor(...)` resolves the company identity, creates or updates the company, and upserts the exhibition participation row.
5. Optional Excel exports read the SQLite database and generate workbooks.

Relevant files and their roles:

- [config.py](./config.py) — project-wide constants: base URLs, domain, timeout, event code, and directory letters.
- [database.py](./database.py) — SQLite schema creation, lookup/update functions, company and exhibition synchronization logic, and upsert behavior.
- [scraper.py](./scraper.py) — live API access, event filtering, and higher-level sync entry points.
- [normalizer.py](./normalizer.py) — text normalization used for company matching.

- [excel_export.py](./excel_export.py) — exports the SQLite data to Excel workbooks.
- [inspect_duplicates.py](./inspect_duplicates.py) — quick inspection script that groups records by normalized company name to surface duplicates.
- [md-sync.ps1](./md-sync.ps1) — primary Windows PowerShell script with short commands for tests, smoke API checks, all-event sync, export, and code validation.
- [gifa.ps1](./gifa.ps1) — compatibility wrapper for the previous helper filename.

The four supported events are configured in `EVENTS` in [config.py](./config.py):
GIFA, METEC, THERMPROCESS, and NEWCAST. They use one generic scraper pipeline and
can be selected without editing scraper logic:

```powershell
python scraper.py METEC
```
- [requirements.txt](./requirements.txt) — runtime/test dependencies: `requests`, `openpyxl`, and `pytest`.
- [data/md-sync.db](./data/md-sync.db) — local SQLite database generated by the application.

- [tests/](./tests/) — pytest suite exercising the API, sync logic, database layer, filtering, and export logic.

The repo also contains Python bytecode caches in `__pycache__` and pytest cache directories. These are generated artifacts and not part of the runtime design.

## Data Flow

The actual execution flow is straightforward:

- Execution starts in [scraper.py](./scraper.py) via module-level calls such as `sync_gifa_2023()` when run as a script.
- `sync_gifa_2023()` calls `sync_event_from_api(...)` with `event_name="GIFA"`, `edition=2023`, and `event_code="GMTN2023.gifa"`.
- `sync_event_from_api(...)` calls `fetch_exhibitors_by_event("GIFA 2023")`.
- `fetch_exhibitors_by_event(...)` iterates `DIRECTORY_LETTERS` (`a` through `z`), calls `fetch_directory_letter(letter)`, and keeps only `type == "profile"` records whose `eventIcons` contain `label == "GIFA 2023"`.
- `sync_event(...)` ensures the exhibition row exists using `get_or_create_exhibition(...)` and then loops through each exhibitor record.
- Each record is written through `database.sync_exhibitor(...)`.
- `sync_exhibitor(...)` uses `find_company(...)` to match an existing company record; if not found, it creates one. It then upserts the participation row in `exhibition_companies`.
- Export functions read from SQLite and generate workbook sheets for summary, companies, and participation records.

## API Integration

### Base URL and endpoint structure

The project currently calls the Messe Düsseldorf directory API endpoints under:

- `https://widgets.messe-duesseldorf.de/vis-api/vis/v1/en/directory`

The code builds URLs like:

- `https://widgets.messe-duesseldorf.de/vis-api/vis/v1/en/directory/a`
- `https://widgets.messe-duesseldorf.de/vis-api/vis/v1/en/directory/b`

The endpoint is a directory listing by letter, not a detail endpoint for individual exhibitors.

### HTTP method, headers, and event parameters

The live requests use HTTP GET. The request headers used in code are:

- `Accept: application/json`
- `User-Agent: Mozilla/5.0`
- `X-Vis-Domain: www.gifa.com`

The code uses `REQUEST_TIMEOUT = 30` in [config.py](./config.py).

### Directory pagination / alphabetical traversal

The code does not implement offset-based pagination. It traverses the alphabet directly:

- `DIRECTORY_LETTERS = "abcdefghijklmnopqrstuvwxyz"`
- `fetch_exhibitors_by_event(...)` iterates each letter and requests that directory page.

### Relevant response fields used by the code

The code currently relies on fields such as:

- `type`
- `id`
- `exh`
- `exhSeoId`
- `name`
- `country`
- `city`
- `location`
- `premium`
- `tags`
- `eventIcons`

The code uses `eventIcons` to match a target event label such as `"GIFA 2023"` and stores the raw `tags` and `eventIcons` data as JSON in the database.
Optional profile values (`email`, `telephone`, product categories,
and product groups) are extracted when present in a response, but none were present
in the sampled directory payload. Company `created_at` is preserved as the first
discovery time, while `updated_at` changes on later observations. Participation
`first_seen_at` is immutable and `last_seen_at` is updated on every successful
observation.

### Identification and current limitations

The application currently identifies an exhibitor record via the `exh` field in the exhibition-specific participation table, not by a separate stable exhibitor-profile ID across all exhibitions. A company is identified by normalized name plus optional country and city using `find_company(...)`.

The directory response does not contain contact or product fields. Profile
enrichment currently provides email, telephone, website, and structured product
categories where the profile publishes them.

## Database

The database is a local SQLite database stored at [data/md-sync.db](./data/md-sync.db).
If an installation still has the former `data/gifa.db` file and no
`data/md-sync.db` file, the first database connection moves it to the new
path without changing its contents.

### Database technology

- SQLite
- Connection created with `sqlite3.connect(...)`
- `row_factory = sqlite3.Row`
- A `get_connection()` context manager ensures commit/rollback and creates the `data` directory if needed.

### Tables and schema

The schema created by `initialize_database()` currently contains:

- `companies`
- `exhibitions`
- `exhibition_companies`
- `product_categories`
- `product_groups`
- `exhibition_company_categories`
- `product_category_groups`
- `sync_metadata`

`companies` includes:

- `id` (INTEGER PRIMARY KEY AUTOINCREMENT)
- `name` and `normalized_name`
- `country` and `normalized_country`
- `city` and `normalized_city`
- `website`
- `email` and `telephone` (when available)
- legacy optional profile JSON columns retained for compatibility
- `created_at`
- `updated_at`

Product categories are retrieved from the profile enrichment endpoint:
`https://finder.messe-duesseldorf.de/vis-api/vis/v1/en/exhibitors/{exh}/slices/profile`.
The response contains `categories[]` entries with `id`, `label`, `catalogIndex`,
`hierarchy[]`, and optional `productList[]`. The hierarchy is stored as normalized
product groups and category associations are tied to the exhibition participation,
not globally to the company. The old company `logo` column is removed during
database initialization; existing non-logo data is preserved.

Indexes include:

- `idx_companies_normalized_name` on `companies(normalized_name)`
- `idx_companies_name_country` on `companies(normalized_name, normalized_country)`

`exhibitions` includes:

- `id` (INTEGER PRIMARY KEY AUTOINCREMENT)
- `event_name`
- `edition`
- `event_code` (UNIQUE)
- `created_at`

`exhibition_companies` includes:

- `id` (INTEGER PRIMARY KEY AUTOINCREMENT)
- `company_id` (foreign key to `companies.id`)
- `exhibition_id` (foreign key to `exhibitions.id`)
- `source_exhibitor_id`
- `seo_id`
- `hall`
- `stand`
- `location`
- `premium`
- `tags_json`
- `event_icons_json`
- `scraped_at`
- `first_seen_at`
- `last_seen_at`
- `changed_at`

Unique constraint:

- `UNIQUE(exhibition_id, source_exhibitor_id)`

Indexes:

- `idx_exhibition_companies_company`
- `idx_exhibition_companies_exhibition`
- `idx_exhibition_companies_source_id`

### Company / exhibition relationships

The model is intentionally normalized:

- One row in `companies` represents the canonical company record.
- One row in `exhibitions` represents an event/edition.
- Many company records can be linked to many exhibitions through `exhibition_companies`.

This means the same company can appear in multiple exhibitions while still keeping a single internal company ID. The current schema supports a company appearing at multiple fairs and multiple editions without duplicating the `companies` row.

### Normalization and duplicate handling

Company matching uses `normalize_company_name(...)` from [normalizer.py](./normalizer.py), which strips punctuation, normalizes Unicode, lowercases, and collapses whitespace. This normalization is then compared against `normalized_name`, `normalized_country`, and `normalized_city`.

The lookup order in `find_company(...)` is:

1. `normalized_name + normalized_country + normalized_city`
2. `normalized_name + normalized_country`
3. `normalized_name` only, but only when unique

This is the key rule for deciding whether an incoming exhibitor record should be treated as the same company as an existing one. It is deterministic but intentionally simple.

### Duplicate semantics currently supported

The system currently distinguishes between the following cases:

- Duplicate exhibitor records: same company record appears multiple times in the same exhibition with a different `source_exhibitor_id`, but the code merges them to one `company_id` while leaving multiple `exhibition_companies` participation rows. The `UNIQUE(exhibition_id, source_exhibitor_id)` constraint prevents exact same source identifier duplicates within one exhibition.
- Multiple exhibitor records belonging to the same company: this is supported by `find_company(...)`, which reuses the same company row when the normalized name/country/city match.
- The same company appearing at multiple exhibitions: supported by reusing the same company row and inserting multiple rows in `exhibition_companies`.
- The same company appearing in multiple editions of an exhibition: also supported in principle because the `exhibitions` table is keyed by `event_code` and company identity is not bound to a single edition. The code can keep the same company row and create new participation rows for later event codes.

The code currently does not track a full historical series of appearances or a separate audit log for every change. It stores `first_seen_at`, `last_seen_at`, and `changed_at` on the exhibition relationship row, but not a comprehensive historical table of snapshots.

### Upsert/update behavior

On company sync:

- `sync_exhibitor(...)` calls `find_company(...)`.
- If no company matches, it creates a new company with `create_company(...)`.
- If a company matches, it updates the company details in `update_company(...)`.

On exhibition participation:

- `upsert_exhibition_company(...)` inserts or updates a row in `exhibition_companies` using `INSERT ... ON CONFLICT(exhibition_id, source_exhibitor_id) DO UPDATE`.
- This keeps the row unique per exhibition and exhibitor ID.
- `last_seen_at` is updated on each scrape; `changed_at` is marked when key participation fields differ from the stored version.

## Synchronization

The synchronization model is event-based and idempotent with a simple duplicate strategy.

### First sync

A first sync creates:

- the exhibition row if the `event_code` is new,
- the company row if no matching company exists,
- the participation row in `exhibition_companies`.

### Re-running the same sync

The application is designed to be repeatable. Running the same sync again does not create a second company row when the same company matches the same normalized identity. The `upsert_exhibition_company(...)` logic also prevents duplicate participation rows when the same `exhibition_id` and `source_exhibitor_id` pair is encountered again.

### What counts as a new record vs an update

- New company: no existing company matches the normalized identity rules.
- Updated company: existing company row is found and its fields are refreshed from the API record.
- New exhibition participation: no row exists for the same `(exhibition_id, source_exhibitor_id)`.
- Updated exhibition participation: the same pair exists, but a field such as `seo_id`, `hall`, `stand`, `location`, `premium`, `tags_json`, or `event_icons_json` changed.

### Deletions and retention behavior

The current code does not implement delete operations for companies or exhibition records. It also does not remove missing API records from prior sync batches.

In other words:

- A missing record in a later API response is not actively deleted from the database.
- Historical records are retained as long as they exist in the database.
- The system does not currently calculate a complete delta of records that disappeared since the last sync.

### Current awareness of discovery and visibility timing

The database includes `first_seen_at`, `last_seen_at`, and `changed_at` on `exhibition_companies`, but the current logic is narrow:

- `first_seen_at` is initialized to `scraped_at` when the row is first inserted.
- `last_seen_at` is updated when the row is seen again.
- `changed_at` is set when key exhibition-participation fields change.

The code does not maintain a separate company-level `first_seen_at` or `last_seen_at` column, and it does not currently compute which companies are new since a previous sync in a dedicated, queryable way.

## Running the Project

### Install dependencies

From the repository root:

```bash
pip install -r requirements.txt
```

### Configure the project

The project does not currently load environment variables from a `.env` file. Configuration is effectively static in [config.py](./config.py). There is no current environment-aware config loader or secret management layer in the repository.

### Initialize the database

The SQLite database is created on demand when the app runs `initialize_database()`. This happens in `database.initialize_database()` and is called before synchronization and export steps.

### Run the scraper / sync

The direct Python entry point is in [scraper.py](./scraper.py):

```bash
python -c "from scraper import sync_gifa_2023; print(sync_gifa_2023())"
```

This fetches the live GIFA 2023 records and writes them to the local SQLite database.

The primary PowerShell helper script [md-sync.ps1](./md-sync.ps1) also supports:

- `./md-sync.ps1 sync`
- `./md-sync.ps1 smoke`
- `./md-sync.ps1 export`
- `./md-sync.ps1 test`
- `./md-sync.ps1 check`

The previous `gifa.ps1` filename remains available as a compatibility wrapper.

### Run exports

To export one specific event edition:

```bash
python -c "from excel_export import export_event; print(export_event('GIFA', 2023))"
```

This creates `exports/GIFA_2023.xlsx`. To export every edition currently stored
in SQLite as separate workbooks, use:

```bash
python -c "from excel_export import export_database_to_excel; print(export_database_to_excel('exports'))"
```

Each workbook contains only the selected event edition, with summary, company
master, and participation records sheets. Product categories and groups are
limited to each exhibition participation.

The tests are grouped by concern:

- [tests/test_record_filtering.py](./tests/test_record_filtering.py) — verifies that only `profile` records for the selected event are retained.
- [tests/test_database.py](./tests/test_database.py) — validates the behavior of company reuse, cross-exhibition reuse, and repeated sync idempotence.
- [tests/test_sync.py](./tests/test_sync.py) — validates that internal sales fields are not overwritten when merging external GIFA data.
- [tests/test_data_protection.py](./tests/test_data_protection.py) — covers the sales-field protection behavior.
- [tests/test_excel_export.py](./tests/test_excel_export.py) — validates the workbook export table formatting.

The tests currently protect:

- API responsiveness and a few URL assumptions
- Event filtering behavior
- Company deduplication and reuse across exhibitions
- Repeated sync safety
- Basic Excel output structure
- Protection of internal sales metadata during merge operations

The suite does not currently appear to cover:

- detailed API error handling or retries
- database migration edge cases beyond a simple initialization path

- historical change tracking beyond basic timestamps

### Test command and result

The project was executed with:

```bash
python -m pytest -q
```

Current actual result at the time of the md-sync transition analysis: 32 passed.

The application-level migration now uses generic `source_exhibitor_id` and
`sync_metadata` identifiers. Existing databases are migrated from the former

## Current Limitations / Known Gaps

The codebase contains a number of real limitations that are visible in the implementation:

- The project stores a few timestamp fields (`first_seen_at`, `last_seen_at`, `changed_at`) but does not maintain a full historical change log.
- There is no clear, reliable company-level `first_seen_at` / `last_seen_at` calculation for all companies across editions.
- The system does not currently compute which companies are new since a previous synchronization in an explicit, queryable way.
- The active event configuration contains the currently supported fairs and editions; future editions must be added as they are published.
- The identity matching rules are based on normalized name/country/city and are not a richer semantic matching system.
- API retries are bounded and specifically handle rate limiting responses.
- Excel export is a reporting/export layer rather than a true data pipeline.

## Future Development Considerations

The next logical areas suggested by the current code are:

- Expand the API layer beyond the directory listing to cover exhibitor detail pages if available.
- Add future-edition entries to the central event configuration as Messe Düsseldorf publishes them.
- Strengthen change tracking and historical visibility without introducing a full audit schema prematurely.
- Improve duplicate matching and company identity heuristics where name/country/city comparisons are insufficient.
- Add more structured logging around network calls and database writes.
- Consider a deliberate strategy for detecting new companies, missing records, and historical appearances across multiple sync runs.

## Summary

The repository currently contains a workable but focused synchronization prototype for GIFA exhibitor data. It successfully scrapes the Messe Düsseldorf directory, identifies company-level duplicates, stores normalized company and exhibition records in SQLite, and exports the data to Excel. It does not yet implement rich profile enrichment, stable historical change tracking, or a generalized multi-fair platform. The codebase is best understood as a practical local-sync prototype built around the GIFA 2023 data source and its current database model.
